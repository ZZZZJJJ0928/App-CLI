# Application runtime and mail maintenance

[简体中文](APPLICATION-RUNTIME.zh-CN.md) · [Lifecycle](LIFECYCLE.md) · [Validation](VALIDATION.md)

The maintenance fork implements `0.3.0-sparkclaw.30`.
Python is packaged as `0.3.0+sparkclaw.30`; the optional Node runtime is
`@infinimesh/app-cli-runtime@0.3.0-sparkclaw.30`. This is a fork release, not an
upstream release. Mail is the first application; the public Registry remains
independent of Node, mail and browsers.

## Execution and ownership

```text
SparkClaw product admission → ProductClient → app-cli --machine
 → Registry.control → RuntimeAdapter 3.0 → fixed transport client
 → owner-local Executor → registered application handler
 → signed BrowserHostPort → SparkClaw task page / Bridge / Desktop
```

The existing Python Registry alone owns public discovery and admission. The
Node binding table maps reviewed commands to internal handlers; it is not an
alternative API. `APP_CLI_CONFIG` selects an owner-private trusted deployment
file, not an option accepted from business input. With no config, calculators
and Runtime v1 remain independent and mutation is denied by default.

`applications/mail` owns QQ Mail, Gmail and Outlook commands, selectors,
account/document checks, provider waits, Reader sources, notification rules and
send journals. Its three manifests and bindings are generated by
`applications/mail/build-bindings.mjs`. `MailboxClient` preserves the product
receipt envelope while every operation crosses the Python Registry.
SparkClaw owns approval, ingestion/storage/UI and the generic browser resources.
No application module imports a SparkClaw checkout or starts a second browser.
The retained `SparkClawMailReader` page ABI is deliberate compatibility, not
ownership of its implementation. Migrated sources/tests/assets retain their
Apache-2.0 license and original commit attribution; the existing core is MIT.

## Adding another control application

1. Implement a backend under `applications/<name>` with a Manifest 1.0 and
   command input/output schemas. Choose a reviewed LifecycleAdapter for writes;
   native/CLI implementations can provide that interface without Node.
2. For this runtime, provide an execution binding conforming to
   [binding schema](../schemas/execution-binding-v1.schema.json), a deterministic
   manifest digest and an explicit internal handler mapping. The trusted
   assembly registers them; never accept import paths or executables from input.
3. Declare only needed Host methods, origins, initialization assets, resource
   lane, effects and timeout. A backend without browser needs no Host entry.
   Non-mail browser and native mutation fixtures demonstrate both paths.
4. Add evidence for intent/owner binding, replay, cancellation, recovery and
   output validation. Rebuild a complete paired release and update consumers'
   generated projections. New applications do not need Registry or scheduler
   modifications when they use existing backend and Host capabilities.

## Persistence, bounds and recovery

The Python service launcher holds an inherited POSIX `flock`. SQLite WAL/FULL
(ledger 2) commits request key, principal, owner, immutable intent, task,
request epoch, dispatch phase and events before side effects. Each launch
advances `execution_epoch`; an atomic `authority.json` high-water mark tracks
epoch and commit sequence, rejecting a missing or older database, including
same-epoch backups. A ledger 1 database migrates in place into the sealed legacy
epoch on first start. Restart blocks unfinished reads, voids unreleased dispatch
reservations (the task stays resumable) and makes released dispatches uncertain,
with an event gap. An optional independent progress anchor (`anchor` in the
deployment config: `none` or `http` over a Unix socket/URL with a bearer token)
confirms every dispatch release and detects whole-set rollback.
Reconciliation reads original send evidence and never clicks Send again. A user
may resolve an uncertain send; resolution never resends.

A handler's completed result is accepted only after output validation and a
final execution-authority, cancellation and deadline check. The Executor then
awaits the Host cleanup attempt before publishing a terminal receipt or accepting
its ACK. If cleanup fails, the validated business result remains completed and
a `host_cleanup_failed` event records the diagnostic reason in the same ledger
transaction. Host resource retirement and cleanup fences remain enforced; this
does not retry the provider action. A later stop during cleanup cannot erase
an already validated result. Invalid or unproved output retains the existing
failure/uncertainty behavior. A crash before the terminal commit still uses
the original durable journal through explicit reconciliation.

A background single writer reclaims terminal tasks only after their request
epoch is sealed and their delivery obligation is met (read results one hour
after ACK or a day without it; delivered sends after ACK plus the receipt
window; resolved sends at once). Legacy epoch rows are retained. Admission uses
measured ledger, WAL and grant storage against a budget with a recovery reserve.
These guarantees do not claim exactly-once remote delivery.

| Boundary | Frozen default |
| --- | --- |
| Public request / arguments / response | 2 MiB / 1.5 MiB / 1 MiB |
| Transport / embedding control budget | 15 seconds / 25 seconds |
| Mail collection maximum business timeout | 1,800 seconds; independent of RPC |
| Watch execution grant / early renewal | 300 seconds / 60 seconds |
| Host heartbeat / activity lease | 10 seconds / at most 30 seconds |
| Watch disconnect recovery budget | 60 seconds, then blocked with a gap |
| Idle read page | At most 30 minutes; no action authority while parked |
| Host large result | Owner-private hash-verified reference, at most 16 MiB |
| Event retention | Last 1,000 events and 2 MiB per task, 32 MiB per owner, cursor gap reported |
| Ledger admission | No cumulative task count limit; 512 MiB allocated database plus measured storage within `storage.budget_bytes` (placeholder 2 GiB) and a recovery reserve; pressure returns `STORAGE_PRESSURE` |
| Product task-access grant | 30 days, separate from execution authority |

A positive integer `maxTasks` opts into a task-count cap; zero disables counting.
Existing databases need no migration and retain their complete request history.

At capacity, new admission fails with `LEDGER_CAPACITY_EXCEEDED`; existing
lookups/replay remain available and deduplication records are never evicted.
This is an admission watermark, not a hard filesystem quota: active results,
events, WAL, grants and mailbox files need additional disk headroom. Do not clear
the ledger or authorization index to resume service; capacity expansion/archival
requires a reviewed maintenance change preserving key history.

Host generation and epoch fence stale calls. Read and watch have separate
activities on the same resource. The actual CLI daemon watches its lease and
uses monotonic expiry even when Controller is lost. Stale Reader/account
preparation invalidates the page; cleanup failure fences reuse. Revoking watch
preserves a valid read activity. Private artifacts enforce ownership, path,
size and digest before consumption. Signed Host messages are specified in the
[Host schema](../schemas/browser-host-v1.schema.json).

## Building and installing

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
npm ci --prefix runtimes/browser --ignore-scripts
.venv/bin/python -W error::ResourceWarning -m unittest discover -s tests -v
npm test --prefix runtimes/browser
.venv/bin/python release/build.py
```

Commit reviewed source before the final build. `dist/release/release.json`
records that source commit, Python source digest and hashes for wheel, npm
archive and pinned Python requirements. Runtime `release.json` pins code,
schemas, manifests, bindings and assets; the wheel embeds its digest. Build
again from the committed source for publication; do not pair artifacts from
separate builds. SparkClaw vendors this complete set and verifies both its
installed consumer package and the configured service runtime.

`python -m app_cli.executor_service /absolute/private/config.json` starts the
owner-local service. Configuration contains fixed Node/assembly/socket paths,
registered binding digests, private signing key and grant directories. A
trusted product issuer publishes immutable signed `{grant, resource, mac}`
files; Python, Executor and Host verify independently. Keys, sessions and user
content are never part of a release.

Install all files first, drain the Executor and Host, then activate the matched
consumer, wheel, npm runtime and Reader/preload projections. Handshake checks
actual release and binding digests. Rollback restores the whole matching set
with a compatible ledger version while retaining the same state directory,
request index, journals and monotonically increasing epoch. Ledger 1 releases
refuse a migrated ledger 2 directory; after activation, rollback must use a
ledger-2-compatible package and must not restore older execution evidence. Unknown
versions or missing authority evidence fail closed. SparkClaw's installer and disposable
paired-release qualifier exercise these steps.

## Validation boundary

The receive page is shared by watches and network-only discovery, capture and
thread inventory for the exact owner, account, scope, credentials and binding.
A connection probe may join only through a current watch with matching
credentials; an unbound probe remains an independent task. Send and mark-read
use independent pages. Each receive task verifies the document/account and
resets transient reader state before and after work. Renewed watch leases keep
the page resident; stopping the watch lets an active read finish, then closes
the page without parking it again. Expiry, revocation and cleanup fences remain
authoritative. Periodic authorization maintenance yields between bounded batches
so directory growth cannot monopolize the Host event loop.

QQ read confirmation rechecks the exact account, message, selection, folder and
receipt timestamp through a fresh bounded native search. It never relies on a
cached read flag or the page's incidental list URL. A visible exact row may be
clicked once; the effect is accepted only after independent provider metadata
confirms read. An interrupted or unknown read journal permits only read-only
confirmation on later invocations, without releasing another write. Preparation
and released attempts are recorded separately, and neither recovery path alters
the captured original or its manifest.

Source Python (86) and optional runtime/provider (444 passed, 2 skipped) tests
pass locally on macOS with Python 3.11 and Node 26.
A fresh installation and two compatible artifact sets verify tamper rejection,
mixed-version rejection, stopped-service activation and state-preserving
rollback. SparkClaw additionally qualifies a non-mail command through the
installed Python Registry, resident Executor and actual isolated Electron task
page, alongside ordinary MCP/CLI tasks and personal-page protection.

Provider tests cover synthetic mail content, account/document checks, send
verification, original-file handling and watch contracts. Automated validation
does not establish live QQ/Gmail/Outlook send/receive acceptance; that remains
part of the paired deployment's separate acceptance.
No cloud CI matrix or non-POSIX lifecycle transport execution is claimed.

## Account identity and delivery addresses

Mail discovery preserves `account_address` as the verified, stable namespace for
Reader checks, captures, message identifiers, send journals and account binding.
It is not necessarily an address that accepts incoming SMTP mail. Discovery may
also return `delivery_address` (at most 320 characters) and `account_aliases`
(1–100 distinct, lowercase addresses). Both fields are either omitted or
returned together, and the delivery address must appear in the aliases.
Range discovery carries the same fields inside `collect_page`'s
`discovery`; the page does not introduce a second identity copy. Consumers must
retain mailbox IDs and existing messages when these observations change, and
exclude all verified aliases when constructing reply-all recipients.

QQ Mail and Gmail use the already verified signed-in account for both roles.
Gmail reads the single visible account button in the page header, verified by its
Google Accounts sign-out-options destination. Its accessible label may be in any
language; conflicting or ambiguous account attributes fail closed. The generated
Reader and native-send fallback share this extraction, preserving expected-account
checks and refusing to repin after an account switch. Login checks still use the
existing compose readiness signal; their optional account hint is not an identity
binding. No message body, account-switcher list or inferred sender supplies identity.
For qualified consumer Outlook pages, the adapter reads the current native
`UserMailbox` configuration and invokes its native default SMTP From/alias
selection. It verifies every candidate against that same mailbox's proxy
addresses, rejects the native internal-routing addresses, and checks that the
mailbox did not change during observation. It does not infer identity or aliases
from received/sent message headers, rewrite internal MSA addresses, or select
a different account. Native module/version failures omit delivery metadata
without promoting the internal identity to a delivery address. Such omission
is not evidence that a previously observed address is still current.

This is address-selection evidence, not a delivery guarantee: recipient policy,
service health and mailbox state can still reject mail. Actual send and receive
qualification remains separate from login checks and synthetic fixture tests.
